# 抖音直播事件推送接入

采集程序把直播间页面显示的消息识别为事件。启用 HTTP 推送后，每条新事件先发起一次请求，随后写入本地 JSONL。实时消息页在本地写入后更新。

## 启用推送

在启动命令中加 `--push-url`，值是消费方提供的完整 HTTP(S) 地址，包含接收路径。省略此参数时，只在本地保存和显示消息。

```cmd
npm.cmd run edge -- "https://live.douyin.com/943959289826" --push-url "http://127.0.0.1:8080/live-events"
```

如果使用独立 Edge 模式，同样可在 `npm.cmd start --` 的参数中加 `--push-url`。

普通 Edge 模式更新后，在 `edge://extensions` 重载「抖音直播消息采集」扩展，再刷新直播标签页。扩展会为分类提供页面结构信息。

## 请求格式

- 方法为 `POST`，`Content-Type` 为 `application/json`。
- `schemaVersion` 当前为 `1`。`events` 是数组，当前每次请求包含一条事件。
- 消费方按 `type` 分发，使用 `data` 读取该类型的字段。建议成功接收后返回 `204 No Content`。

```json
{
  "schemaVersion": 1,
  "events": [
    {
      "eventId": "a994a09b-5101-4d29-bc83-41b93b15a9cc",
      "roomId": "943959289826",
      "type": "gift",
      "capturedAt": "2026-11-15T12:30:01.000Z",
      "actor": { "nickname": "某观众" },
      "data": { "giftName": "小心心", "displayCount": 4 },
      "rawText": "某观众：送出了 小心心 × 4"
    }
  ]
}
```

| 字段 | 类型 | 用途 |
| --- | --- | --- |
| `eventId` | 字符串 | 采集程序生成的 UUID，标识本次观察到的事件 |
| `roomId` | 字符串 | 直播间链接里的数字编号 |
| `type` | 字符串 | 事件类型，见下表 |
| `capturedAt` | 字符串 | 采集时间，ISO 8601 格式 |
| `actor` | 对象或 `null` | 能从页面识别昵称时为 `{ "nickname": "…" }`，否则为 `null`。昵称可能重复 |
| `data` | 对象 | 按事件类型提供的附加字段，可为空对象 |
| `rawText` | 字符串 | 页面中采集到的整条消息文本 |

## 事件类型

豆姐导播台沿用采集器的 v1 信封。也可以用风环岛的简写格式，直接 POST 用户事件对象、事件数组或 `{"events":[...]}`。简写格式可以使用非空字符串作为房间和事件 ID；可省略 `capturedAt` 和 `rawText`。

```json
{
  "roomId": "rehearsal",
  "eventId": "guest-01",
  "type": "comment",
  "actor": { "nickname": "小林", "userId": "viewer-42" },
  "data": { "content": "老板说，公司就是我第二个家。" }
}
```

同一场直播里若要接住同一位观众的追问，建议传稳定的字符串账号标识。依次识别 `actor.secUid`、`actor.openId`、`actor.userId`。采集器只有昵称时也可使用。只有已在舞台播出的内容会进入上下文。

| `type` | 含义 | `data` 字段 |
| --- | --- | --- |
| `comment` | 普通评论 | `content`，评论正文字符串。只有不可读取的表情时为 `[表情]` |
| `like` | 点赞提示 | `{}`。可触发一次点赞反馈，具体点赞量未知 |
| `room_join` | 进场提示 | 单人进场通常为 `{}`。汇总提示可有 `countText`（数量文本）。`displayCount`（数字）仅在页面展示确切整数时提供 |
| `gift` | 送礼提示 | `giftName`（字符串）和 `displayCount`（数字），可识别时提供 |
| `follow` | 关注主播 | `{}` |
| `fans_club_join` | 加入粉丝团 | `{}` |
| `unknown` | 其他提示或暂无法识别的消息 | `{}`，消费方可以记录 `rawText` |

送出「粉丝团灯牌」属于 `gift`。送礼连击和多人进场可能以汇总数显示，`displayCount` 适合展示，消费方应避免把每条展示数直接计入新增总数。关注和加入粉丝团已有类型定义，现存采集样本尚未验证这两类通知。实际覆盖范围以页面显示为准。

若采集器能识别送礼连击批次，可在 `data.comboId` 中传同一串连击共用的字符串。比如一位观众同一连击依次送出玫瑰 ×1、×3、×5，舞台展示最新累计数，队列按合计五份答谢。重复推送相同的房间与事件 ID 会被去重。

## 并发与失败处理

每条事件独立发起请求。本地保存不等待 HTTP 响应，推送失败时仍会保存。上一条请求未结束时，后续事件仍可发送。请求可能乱序到达，消费方需要支持并发处理。每个请求超时 5 秒，接收失败、超时或返回重定向时均结束该次尝试，程序继续采集。历史 JSONL 和失败事件均不补发。相同内容在页面上作为两条消息出现时，会产生两个独立的 `eventId`。
